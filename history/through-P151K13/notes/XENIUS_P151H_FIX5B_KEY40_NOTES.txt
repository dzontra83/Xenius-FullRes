THE MINIMAL FIX5B PATCH
Built directly from P151H FIX4, NOT from FIX5A.
- classes.dex, native libs, resources, camera opening/closing code, 50MP buffer handling, dynamic 2F/3F/5F, DNG cleanup: byte-for-byte identical to working-capture FIX4.
- classes2.dex, method LMC/c2a.getC2apiPref (method index 646), code unit CU340: the original existing if-nez v4 condition now branches to the original early return CU485 when there is already an active marker in LMC/main.Aemodef. The preexisting P151H ACQUIRE_RETAIN handler (which incremented the counter each time requests were built) is thus not used by this path. This restores the idempotent behavior already present in original P151C while leaving P151H's journal/release logic intact.
- The only executable difference from FIX4 is one byte at the CU341 branch displacement, 215 -> 145.
- This protects against repeated request-building acquisitions leaking the in-process counter, while retaining request-time first activation when no gate was already acquired.

LIMITATIONS
FIX5B is an EXPERIMENTAL balance repair, not a completed RawR-style camera-close rewrite. The alternate Larb camera close path still releases after CameraDevice.close() returns, rather than a confirmed onClosed callback; asynchronous camera close and overlap with another camera open can still be problematic. The existing journal implementation is not camera-idle protected and does not independently log getInfo(40) readback. Also note that with an already enabled key40 value of 1 before the test, restoration can correctly restore 1 instead of 0; establish starting value explicitly when not in active capture.
