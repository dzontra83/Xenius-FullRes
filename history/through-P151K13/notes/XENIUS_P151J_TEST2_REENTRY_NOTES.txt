WHY
User reports P151J TEST1 works only on first launch; after background/reentry JPEG capture stops. After external key40 OFF=0, reentering Xenius does not set key40=1. The original P151C helper tracks key40 via in-process static LMC/main.Aemodef; its acquire branch at code-unit 340 returns without reading actual key40 when Aemodef is nonzero. P151J TEST1 activates only at Activity.onCreate, which does not run on every resume.

PATCH (experimental)
1. New CameraActivity.onResume code item, 34 -> 38 code units: prefix invokes LMC/c2a.getC2apiPref(null) before original method body. Original onResume method body unchanged; has no try blocks, original branch targets shifted by +4 code units.
2. In classes2.dex original LMC/c2a.getC2apiPref, at CU340 change IF-NEZ branch offset from +145 (return) to +2 (fall through to the original vendor getInfo(40) path). Thus Aemodef no longer prevents rechecking the actual key40 state; if external app turned it OFF while process remains open, the helper can set it ON again, without incrementing a counter.
3. Preserve all other methods including P151J onCreate early activation, original camera close calls and FIX2 automatic DNG cleanup; all native libraries untouched. NO CameraDevice.onClosed redesign is included. No new persistent journal or independent readback after setValue is added.

LIMITATIONS
- This only targets missing key40 activation on Activity re-entry, and the stale in-process marker. It does not fix an otherwise stuck Camera2 session or RAW Image already closed error. It may not fix a camera session that was configured while key40=0; a fresh camera-device open may be necessary.
- The original gate's stale journal/close races and stock camera conflict remain; test key40 OFF and stock camera only after Xenius is fully closed and camera idle.
- If gate still reads 1 but no photo is saved, this patch has NOT proved the cause; collect logs rather than patch again blindly.
